## 3. Before vs After Behavior
* **Before:** Rules blindly trusted `track["centroid"]` and `track["previous_centroid"]` leading to potential KeyErrors or TypeErrors if the tracker failed to yield clean data for a single frame. Rules evaluated all objects identically without filtering logic.
* **After:** Rules defensively validate centroids using `has_valid_centroid()`. Malformed or missing data is gracefully ignored, allowing the track to continue in the pipeline without crashing the engine. Target class filtering (`target_classes`) ensures only relevant objects trigger alerts (e.g., cars ignored in a pedestrian-only zone).

## 4. Rule Input Contract
The rules uniformly consume the tracking dictionaries outputted by `TrackerService`. The confirmed schema natively includes:
- `track_id` (int)
- `class_name` (str)
- `centroid` and `previous_centroid` (Dict[str, float] containing "x" and "y")
- `direction` ("UP", "DOWN", "LEFT", "RIGHT", or "UNKNOWN")
- `confidence` (float)

## 5. Restricted Zone Implementation
- Safely validates `centroid` keys prior to polygon evaluation (`is_point_in_polygon`).
- Added robust condition checking for `ENTER`, `EXIT`, and `INSIDE` states using delta between `previous_centroid` and `centroid`.
- Integrates `target_classes` filtering to skip evaluation for non-target objects.

## 6. Virtual Fence Implementation
- Requires valid numerical mappings for both `centroid` and `previous_centroid`.
- Accurately computes `lines_intersect` crossing between previous position and current position.
- State is heavily isolated and protected by the Phase 5 cooldown.

## 7. Wrong Direction Implementation
- Natively reads the ByteTrack `direction` key generated by comparing the current centroid with a 3-frame historical centroid.
- A critical edge case—*insufficient movement*—is cleanly handled by the tracker outputting `"UNKNOWN"` when centroid displacement is below `stationary_thresh`. The Rule ignores `"UNKNOWN"`, thereby completely eliminating noise/jitter-induced false direction triggers.

## 8. Loitering Implementation
- Validates the centroid boundary conditions cleanly.
- Maintains isolated state purely via `track_id` in `entry_times`.
- Lifecycle memory-leak bug addressed in Phase 5 via `clean_expired_tracks` is natively hooked and utilized.

## 9. Night Activity Implementation
- Validates current time against `NIGHT_START_TIME` and `NIGHT_END_TIME`.
- **Overnight Time-ranges:** Tested and validated that the logic securely handles overnight crossings (e.g., `22:00 -> 06:00`) utilizing safe conditional branches (`start <= end` vs `now >= start or now <= end`).
- Correctly functions alongside the pipeline's ambient severity-elevation system.

## 10. State / Cooldown Behavior
- Short-term event debouncing is effectively offloaded to the overarching `RuleEngine` architecture (`check_cooldown`). 
- Persistent rule states (like `LoiteringRule` time-stamping) are locally constrained per `track_id` and deterministically collected.

## 11. Edge Cases Handled
- Track missing `"centroid"` -> Rule gracefully skips.
- Track missing `"y"` coordinate -> Rule gracefully skips.
- Sub-pixel tracking jitter -> Ignored via directional `"UNKNOWN"` assignment.
- Invalid Night Time Config -> Degrades to daytime defaults securely.
- Cross-rule Failure Isolation -> One malformed rule exception doesn't halt pipeline execution.

## 13. Remaining Limitations
- Rule configurations (polygons, lines, rules themselves) remain hardcoded inside application memory/setup.
- `EventService` effectively logs to console/stdout rather than a durable database backend.

## 14. Recommended Phase 7 Starting Point

We should introduce SQLAlchemy or a similar ORM layer so the `RuleEngine` can be dynamically seeded by database entries for zones, fences, and rules, and the `EventService` can persist events historically for the dashboard.
